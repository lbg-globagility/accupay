====================================================================
ACCUPAY SELF-SERVICE API DOCUMENTATION
Create / Filing endpoints
====================================================================

Base URL   : /api/self-service
Auth       : Authorization: Bearer <token>   (all endpoints below require [Authorize])
Content-Type: application/json

General notes
--------------------------------------------------------------------
- "EmployeeNumber" is the employee's EmployeeNo (e.g. "EMP-0001"). The
  server looks it up via IEmployeeRepository.GetByEmployeeNumberAsync,
  which matches an ACTIVE employee only, regardless of organization.
  An unknown/inactive EmployeeNumber returns an error - it is not
  silently ignored.
- Date-only fields (Date, StartDate, DateFrom/DateTo, LogDate) accept
  either "yyyy-MM-dd" or a full ISO 8601 datetime; only the date part
  is used.
- Date+time fields (StartTime, EndTime, Time, etc.) accept full ISO
  8601 datetimes; only the time-of-day part is used together with the
  related date field.
- Fields marked (required) are enforced by [Required] model validation
  and will return HTTP 400 if missing.
- Records already approved in Zoho People: the create (POST) calls for
  leaves, overtimes and timelog filings accept an optional "status"
  key:
    "Pending"  - default when the key is left out; the filing waits
                 for approval in AccuPay, as before.
    "Approved" - the record is saved as already approved; no approval
                 email or approval step is needed.
  The value is case-insensitive. Any other value (including
  "Rejected") returns HTTP 400. PUT/DELETE only work on Pending
  filings, so a record created as Approved cannot be edited or deleted
  through this API afterwards.
- Business-rule errors raised by these calls (e.g. an invalid status
  or a duplicate approved record) return HTTP 400 with a body like
  {"Error": "<message>"}.


====================================================================
1. EMPLOYEE - Create
====================================================================
POST /api/self-service/employees

No permission check is enforced beyond being authenticated (no
"EmployeeCreate" permission required).

Request body (CreateEmployeeDto):
  employeeNo          string    (required)
  firstName           string    (required)
  lastName            string    (required)
  middleName          string
  birthdate           date      (required)
  address             string
  landlineNo          string
  mobileNo            string
  emailAddress        string
  tin                 string
  sssNo               string
  philHealthNo        string
  pagIbigNo           string
  employmentStatus    string    (required)
  employmentPolicy    string
  startDate           date
  regularizationDate  date
  employmentPolicyId  int       (id of an existing EmploymentPolicy)
  positionId          int       (id of an existing Position)
  approverIds         int[]     (approver employee ids, optional)

Example:
{
  "employeeNo": "EMP-0001",
  "firstName": "Juan",
  "lastName": "Dela Cruz",
  "middleName": "Santos",
  "birthdate": "1995-04-12",
  "address": "123 Rizal St., Quezon City",
  "landlineNo": "028123456",
  "mobileNo": "09171234567",
  "emailAddress": "juan.delacruz@example.com",
  "tin": "123-456-789-000",
  "sssNo": "34-1234567-8",
  "philHealthNo": "12-345678901-2",
  "pagIbigNo": "1234-5678-9012",
  "employmentStatus": "Regular",
  "startDate": "2026-09-01",
  "regularizationDate": "2026-12-01"
}

Response: EmployeeDto of the created employee.

2. LEAVE - File a leave
====================================================================
POST   /api/self-service/leaves
PUT    /api/self-service/leaves     (edit a pending leave filing)
DELETE /api/self-service/leaves     (delete a pending leave filing)

There is no {id} in the URL for PUT/DELETE. The target Leave filing is
looked up by employeeNumber + startDate instead (must match a Leave
row that is still Status = "Pending" - there is only ever one per
employee per calendar day).

Request body (SelfServiceCreateLeaveDto) for POST and PUT:
  employeeNumber   string          (required)
  leaveType        string          (required)
  leaveTiming      "Day" | "Hour"  (required)
  dateTimes        date[]          (required when leaveTiming = "Day")
  startDate        date            (used when leaveTiming = "Hour";
                                     on PUT this also identifies which
                                     existing filing to edit)
  startTime        datetime        (used when leaveTiming = "Hour")
  endTime          datetime        (used when leaveTiming = "Hour")
  reason           string
  status           string          (optional) "Pending" (default) or
                                     "Approved". POST only - ignored on
                                     PUT (an edited filing stays
                                     "Pending").

Example - whole day(s), one Leave row is created per date in dateTimes:
{
  "employeeNumber": "EMP-0001",
  "leaveType": "Vacation Leave",
  "leaveTiming": "Day",
  "dateTimes": ["2026-09-10", "2026-09-11"],
  "reason": "Family trip"
}

Example - partial day (hourly):
{
  "employeeNumber": "EMP-0001",
  "leaveType": "Sick Leave",
  "leaveTiming": "Hour",
  "startDate": "2026-09-10",
  "startTime": "2026-09-10T13:00:00",
  "endTime": "2026-09-10T17:00:00",
  "reason": "Doctor's appointment"
}

Example - leave already approved in Zoho People (saved as Approved):
{
  "employeeNumber": "EMP-0001",
  "leaveType": "Vacation Leave",
  "leaveTiming": "Day",
  "dateTimes": ["2026-09-10", "2026-09-11"],
  "reason": "Family trip",
  "status": "Approved"
}

Response: list of LeaveDto (one per date created/updated).

Example - Delete:
DELETE /api/self-service/leaves?employeeNumber=EMP-0001&date=2026-09-10

Notes:
- Update/Delete only work while the filing's Status is "Pending" and
  it has not already been emailed; if no matching pending filing is
  found for that employeeNumber + date, the request returns 404.
- With "status": "Approved", every date in the request is saved as
  Approved. The usual leave balance and closed pay period checks still
  apply. A date that already has a leave for the employee (in any
  status) is rejected with HTTP 400, so re-sending the same approved
  leave does not create a duplicate.

3. OVERTIME - File an overtime
====================================================================
POST   /api/self-service/overtimes
PUT    /api/self-service/overtimes     (edit a pending overtime filing)
DELETE /api/self-service/overtimes     (delete a pending overtime filing)

There is no {id} in the URL for PUT/DELETE. The target Overtime filing
is looked up by employeeNumber + startDate instead (must match an
Overtime row that is still Status = "Pending" - only one per employee
per calendar day). On PUT, startDate identifies the existing filing
to edit; it cannot be used to move the filing to a different date.

Request body for POST (SelfServiceCreateOvertimeDto):
  employeeNumber   string    (required)
  startDate        date      (required)
  startTime        datetime  (required)
  endTime          datetime  (required)
  reason           string
  status           string    (optional) "Pending" (default) or
                             "Approved"

Request body for PUT (SelfServiceUpdateOvertimeDto) - same as above
minus "status":
  employeeNumber   string    (required)
  startDate        date      (required)
  startTime        datetime  (required)
  endTime          datetime  (required)
  reason           string

Example (POST):
{
  "employeeNumber": "EMP-0001",
  "startDate": "2026-09-10",
  "startTime": "2026-09-10T18:00:00",
  "endTime": "2026-09-10T21:00:00",
  "reason": "Month-end closing"
}

Example (POST) - overtime already approved in Zoho People (saved as
Approved):
{
  "employeeNumber": "EMP-0001",
  "startDate": "2026-09-10",
  "startTime": "2026-09-10T18:00:00",
  "endTime": "2026-09-10T21:00:00",
  "reason": "Month-end closing",
  "status": "Approved"
}

Response: OvertimeDto.

Example - Delete:
DELETE /api/self-service/overtimes?employeeNumber=EMP-0001&date=2026-09-10

Notes:
- If no matching pending filing is found for that employeeNumber +
  date, PUT/DELETE return 404.
- With "status": "Approved", the overtime is saved as Approved. If the
  employee already has an Approved overtime on the same date with the
  same start and end time (to the minute), the request is rejected
  with HTTP 400, so re-sending the same approved overtime is not paid
  twice. A different time range on the same date is still accepted.
- A new overtime (Pending or Approved) is rejected with HTTP 400 while
  the employee has a Pending overtime filing on the same date.

4. SHIFT - Create a schedule across a date range
====================================================================
POST /api/self-service/shifts

Creates one Shift row per calendar day from dateFrom to dateTo
(inclusive), all using the same start/end/break settings. Only the
time-of-day portion of startTime/endTime/breakStartTime is used; the
actual date comes from each day in the range.

Request body (SelfServiceCreateShiftDto):
  employeeNumber      string    (required)
  dateFrom            date      (required)
  dateTo              date      (required, must not be before dateFrom)
  startTime           datetime  (required)
  endTime             datetime  (required)
  breakStartTime       datetime
  breakLength          decimal   (hours)
  isRestDay            bool
  requiresLunchInOut   bool

Example:
{
  "employeeNumber": "EMP-0001",
  "dateFrom": "2026-09-08",
  "dateTo": "2026-09-12",
  "startTime": "2026-09-08T08:00:00",
  "endTime": "2026-09-08T17:00:00",
  "breakStartTime": "2026-09-08T12:00:00",
  "breakLength": 1,
  "isRestDay": false,
  "requiresLunchInOut": true
}

Response: list of EmployeeDutyScheduleDto, one per date created.

5. TIMELOG - Check In / Lunch Out / Lunch In / Check Out
====================================================================
POST /api/self-service/timelogs                  (Check In)
PUT  /api/self-service/timelogs                   (Check Out)
PUT  /api/self-service/timelogs/lunch-out         (Lunch Out)
PUT  /api/self-service/timelogs/lunch-in          (Lunch In)

There is no {id} in the URL. Check Out/Lunch Out/Lunch In all locate
the existing TimeLog row via employeeNumber + date in the request body
(there is only ever one TimeLog row per employee per calendar day,
created by Check In). All four actions share the same request DTO
(SelfServiceCreateTimeLogDto); each action only reads the field(s)
relevant to it, but employeeNumber and date are always required by
model validation.

Request body (SelfServiceCreateTimeLogDto):
  employeeNumber   string    (required)
  date             date      (required)
  startTime        datetime  (used by Check In)
  endTime          datetime  (used by Check Out)
  lunchOut         datetime  (used by Lunch Out)
  lunchIn          datetime  (used by Lunch In)
  branchId         int       (used by Check In)

Example - Check In:
POST /api/self-service/timelogs
{
  "employeeNumber": "EMP-0001",
  "date": "2026-09-04",
  "startTime": "2026-09-04T08:00:00",
  "branchId": 1
}

Example - Lunch Out:
PUT /api/self-service/timelogs/lunch-out
{
  "employeeNumber": "EMP-0001",
  "date": "2026-09-04",
  "lunchOut": "2026-09-04T12:00:00"
}

Example - Lunch In:
PUT /api/self-service/timelogs/lunch-in
{
  "employeeNumber": "EMP-0001",
  "date": "2026-09-04",
  "lunchIn": "2026-09-04T13:00:00"
}

Example - Check Out:
PUT /api/self-service/timelogs
{
  "employeeNumber": "EMP-0001",
  "date": "2026-09-04",
  "endTime": "2026-09-04T17:00:00"
}

Response: TimeLogDto.

Note: Check In rejects a duplicate check-in for the same employee and
date (employee already has a TimeIn recorded for that date).

6. TIMELOG FILING - Create / Update / Delete
====================================================================
POST   /api/self-service/timelogs/filings
PUT    /api/self-service/timelogs/filings     (edit a pending filing)
DELETE /api/self-service/timelogs/filings     (delete a pending filing)

Used to file a manual correction/request (e.g. forgot to time in/out)
that requires approval, as opposed to a live Check In/Out. A
correction that was already approved in Zoho People can be sent with
"status": "Approved" to update the employee's time log right away.

There is no {id} in the URL for PUT/DELETE. The target filing is
looked up by employeeNumber + logDate + entryType instead (must match
a filing that is still Status = "Pending" - only one per employee per
day per entryType, since an employee could have separate pending
filings for e.g. "CheckIn" and "CheckOut" on the same date).

Request body for POST (CreateEmployeeTimelogFilingDto):
  employeeNumber   string
  entryType        string    "CheckIn" | "CheckOut" | "LunchOut" |
                             "LunchIn" (see notes below)
  logDate          date
  time             datetime
  reason           string
  status           string    (optional) "Pending" (default) or
                             "Approved"

Example:
{
  "employeeNumber": "EMP-0001",
  "entryType": "CheckIn",
  "logDate": "2026-09-04",
  "time": "2026-09-04T08:05:00",
  "reason": "Forgot to time in due to system downtime"
}

Example - correction already approved in Zoho People (applied to the
time log right away):
{
  "employeeNumber": "EMP-0001",
  "entryType": "CheckIn",
  "logDate": "2026-09-04",
  "time": "2026-09-04T08:05:00",
  "reason": "Forgot to time in due to system downtime",
  "status": "Approved"
}

Response: { "id": <filingId>, "status": "Pending" | "Approved" }

Request body for PUT (UpdateEmployeeTimelogFilingDto) - employeeNumber,
logDate and entryType together identify which existing filing to
update, so entryType cannot itself be changed by this call:
  employeeNumber   string
  entryType        string    (identifies the filing; not changed)
  logDate          date      (identifies the filing)
  time             datetime
  reason           string
  decidedBy        string

Example:
PUT /api/self-service/timelogs/filings
{
  "employeeNumber": "EMP-0001",
  "entryType": "CheckIn",
  "logDate": "2026-09-04",
  "time": "2026-09-04T08:00:00",
  "reason": "Corrected time"
}

Example - Delete:
DELETE /api/self-service/timelogs/filings?employeeNumber=EMP-0001&date=2026-09-04&entryType=CheckIn

Notes:
- Only filings with Status = "Pending" that have not already been
  emailed for approval can be edited/deleted; otherwise the API throws
  an error.
- If no matching pending filing is found for that employeeNumber +
  logDate + entryType, PUT/DELETE return 404.
- entryType decides which part of the day's time log the filing
  updates once approved: CheckIn = time in, CheckOut = time out,
  LunchOut = lunch out, LunchIn = lunch in. A Pending filing still
  accepts other text, but approving it later will not change the time
  log.
- With "status": "Approved", the time is written to the employee's
  time log for logDate immediately (the time log is created if the
  employee has none for that date yet) and the filing is saved as
  Approved. entryType must then be one of the four values above
  (case-insensitive), otherwise HTTP 400. If the employee already has
  an Approved filing with the same logDate, entryType and time (to the
  minute), the request is rejected with HTTP 400, so re-sending the
  same approved correction is not recorded twice.
