====================================================================
ACCUPAY SELF-SERVICE API DOCUMENTATION
====================================================================

Base URL   : /api/self-service
Content-Type: application/json

Authentication
--------------------------------------------------------------------
- Only the Approvers and Official Businesses controllers carry
  [Authorize]. Their endpoints need "Authorization: Bearer <token>"
  and return HTTP 401 without one.
- The Employees, Leaves, Overtimes, Shifts and TimeLogs controllers
  have no [Authorize]. Their endpoints can be called without a login
  token. The create/update/delete calls identify the employee by
  "employeeNumber" in the request instead of by the login.
- Some endpoints on those controllers still read the logged-in
  employee from the token. They are marked "(uses login)" below.
  Without a token they fail or return no useful data, so send a
  Bearer token when calling them.

General notes
--------------------------------------------------------------------
- "EmployeeNumber" is the employee's EmployeeNo (e.g. "EMP-0001"). The
  server looks it up via IEmployeeRepository.GetByEmployeeNumberAsync,
  which matches an ACTIVE employee only, regardless of organization.
  An unknown/inactive EmployeeNumber returns an error - it is not
  silently ignored.
- Date-only fields (Date, StartDate, DateFrom/DateTo, LogDate) accept
  either "yyyy-MM-dd" or a full ISO 8601 datetime; only the date part
  is used.
- Date+time fields (StartTime, EndTime, CheckIn, etc.) accept full ISO
  8601 datetimes; only the time-of-day part is used together with the
  related date field.
- Fields marked (required) are enforced by [Required] model validation
  and will return HTTP 400 if missing.
- Records already approved in Zoho People: the create (POST) calls for
  leaves, overtimes and timelog filings accept an optional "status"
  key:
    "Pending"  - default when the key is left out; the filing waits
                 for approval in AccuPay, as before.
    "Approved" - the record is saved as already approved; no approval
                 email or approval step is needed.
  The value is case-insensitive. Any other value (including
  "Rejected") returns HTTP 400. PUT/DELETE only work on Pending
  filings, so a record created as Approved cannot be edited or deleted
  through this API afterwards.
- Business-rule errors (e.g. an invalid status, a duplicate record or
  an exceeded leave balance) return HTTP 400 with a body like
  {"Error": "<message>"}.
- Some checks throw a plain error instead and return HTTP 500. These
  are editing or deleting a filing that is no longer Pending or was
  already emailed for approval, and the "(uses login)" list endpoints
  called without a token.
- Paged GET endpoints accept these query parameters:
    pageIndex  int     (0-based, default 0)
    pageSize   int     (default 10)
    sort       string
    direction  string  ("asc" / "desc")
    all        bool    (true returns every row)
  The response is a PaginatedList: { items, totalCount, pageNumber,
  totalPages }.

1. EMPLOYEE - Create
====================================================================
POST /api/self-service/employees

No login token or permission is required.

Request body (CreateEmployeeDto):
  employeeNo          string    (required)
  firstName           string    (required)
  lastName            string    (required)
  middleName          string
  birthdate           date      (required)
  address             string
  landlineNo          string
  mobileNo            string
  emailAddress        string
  tin                 string
  sssNo               string
  philHealthNo        string
  pagIbigNo           string
  employmentStatus    string    (required)
  employmentPolicy    string
  startDate           date
  regularizationDate  date
  employmentPolicyId  int       (id of an existing EmploymentPolicy)
  positionId          int       (id of an existing Position)
  approverIds         int[]     (approver employee ids, optional)

Example:
{
  "employeeNo": "EMP-0001",
  "firstName": "Juan",
  "lastName": "Dela Cruz",
  "middleName": "Santos",
  "birthdate": "1995-04-12",
  "address": "123 Rizal St., Quezon City",
  "landlineNo": "028123456",
  "mobileNo": "09171234567",
  "emailAddress": "juan.delacruz@example.com",
  "tin": "123-456-789-000",
  "sssNo": "34-1234567-8",
  "philHealthNo": "12-345678901-2",
  "pagIbigNo": "1234-5678-9012",
  "employmentStatus": "Regular",
  "startDate": "2026-09-01",
  "regularizationDate": "2026-12-01"
}

Response: EmployeeDto of the created employee.

Notes:
- An employeeNo or emailAddress that another employee already uses
  is rejected with HTTP 400 ("Employee number '...' is already in
  use." / "Email address '...' is already in use.").

2. LEAVE
====================================================================
GET    /api/self-service/leaves                     (list, uses login)
GET    /api/self-service/leaves/{id}                (get one filing)
POST   /api/self-service/leaves                     (file a leave)
PUT    /api/self-service/leaves/{id}                (edit a pending filing)
DELETE /api/self-service/leaves/{id}                (delete a pending filing)
POST   /api/self-service/leaves/filings/{id}/send-approval-email
GET    /api/self-service/leaves/leave-types         (uses login)
GET    /api/self-service/leaves/leave-statuses
GET    /api/self-service/leaves/leave-balance       (uses login)

A leave "filing" is the group of Leave rows created by one POST (one
row per date). {id} is the id of any Leave row in that filing. GET,
PUT, DELETE and send-approval-email act on the whole filing.

Request body (SelfServiceCreateLeaveDto) for POST and PUT:
  employeeNumber   string          (required)
  leaveType        string          (required)
  leaveTiming      "Day" | "Hour"  (required by the server; any other
                                     value returns HTTP 400)
  dateTimes        date[]          (required - must be present; send
                                     [] when leaveTiming = "Hour". For
                                     "Day" it needs at least one date)
  startDate        date            (used when leaveTiming = "Hour")
  startTime        datetime        (required when leaveTiming = "Hour")
  endTime          datetime        (required when leaveTiming = "Hour")
  reason           string
  status           string          (optional) "Pending" (default) or
                                     "Approved". POST only - ignored on
                                     PUT (an edited filing stays
                                     "Pending").

Example - whole day(s), one Leave row is created per date in dateTimes:
POST /api/self-service/leaves
{
  "employeeNumber": "EMP-0001",
  "leaveType": "Vacation Leave",
  "leaveTiming": "Day",
  "dateTimes": ["2026-09-10", "2026-09-11"],
  "reason": "Family trip"
}

Example - partial day (hourly):
POST /api/self-service/leaves
{
  "employeeNumber": "EMP-0001",
  "leaveType": "Sick Leave",
  "leaveTiming": "Hour",
  "dateTimes": [],
  "startDate": "2026-09-10",
  "startTime": "2026-09-10T13:00:00",
  "endTime": "2026-09-10T17:00:00",
  "reason": "Doctor's appointment"
}

Example - leave already approved in Zoho People (saved as Approved):
POST /api/self-service/leaves
{
  "employeeNumber": "EMP-0001",
  "leaveType": "Vacation Leave",
  "leaveTiming": "Day",
  "dateTimes": ["2026-09-10", "2026-09-11"],
  "reason": "Family trip",
  "status": "Approved"
}

Response (POST/PUT): list of LeaveDto, one per date in the filing.
Each LeaveDto also carries "dateTimes", the full list of dates in
the filing.

Example - Edit (replaces the whole filing with the new dates):
PUT /api/self-service/leaves/123
{
  "employeeNumber": "EMP-0001",
  "leaveType": "Vacation Leave",
  "leaveTiming": "Day",
  "dateTimes": ["2026-09-11", "2026-09-12"],
  "reason": "Family trip (moved)"
}

Example - Delete (deletes every date in the filing):
DELETE /api/self-service/leaves/123

GET /api/self-service/leaves/{id}
  Response: LeaveDto, with "dateTimes" listing every date in the
  filing. 404 if the id does not exist.

GET /api/self-service/leaves (uses login)
  Lists the logged-in employee's leaves. Query parameters: the paged
  parameters above, plus searchTerm, dateFrom, dateTo.
  Response: PaginatedList of LeaveDto.

POST /api/self-service/leaves/filings/{id}/send-approval-email
  Emails the employee's approvers an approve/reject link for the
  filing and marks the filing as emailed. Only Pending filings can be
  emailed. The employee must have at least one approver with an email
  address. A resend is only allowed after the previous link has
  expired. Otherwise HTTP 400. No request body; response is 200 OK.

GET /api/self-service/leaves/leave-types (uses login)
  Response: string[] of the organization's leave type names.

GET /api/self-service/leaves/leave-statuses
  Response: string[] of leave statuses (e.g. "Pending", "Approved",
  "Rejected").

GET /api/self-service/leaves/leave-balance (uses login)
  Response: [{ "leaveType": "...", "balance": <hours> }, ...] for the
  logged-in employee.

Notes:
- PUT/DELETE only work while the filing's Status is "Pending" and it
  has not been emailed for approval yet (HTTP 500 otherwise).
- PUT returns 404 if the id does not exist or the filing does not
  belong to the employee in employeeNumber. DELETE returns 404 if the
  id does not exist.
- With "status": "Approved", every date in the request is saved as
  Approved. The usual leave balance and closed pay period checks still
  apply. A date that already has a leave for the employee (in any
  status) is rejected with HTTP 400, so re-sending the same approved
  leave does not create a duplicate.

3. OVERTIME
====================================================================
GET    /api/self-service/overtimes                  (list, uses login)
GET    /api/self-service/overtimes/{id}             (get one filing)
POST   /api/self-service/overtimes                  (file an overtime)
PUT    /api/self-service/overtimes/{id}             (edit a pending filing)
DELETE /api/self-service/overtimes/{id}             (delete a pending filing)
POST   /api/self-service/overtimes/filings/{id}/send-approval-email

Request body for POST (SelfServiceCreateOvertimeDto):
  employeeNumber   string    (required)
  startDate        date      (required)
  startTime        datetime  (required)
  endTime          datetime  (required)
  reason           string
  status           string    (optional) "Pending" (default) or
                             "Approved"

Request body for PUT (SelfServiceUpdateOvertimeDto) - same as above
minus "status". startDate, startTime, endTime and reason replace the
filing's current values, so PUT can move the filing to another date:
  employeeNumber   string    (required)
  startDate        date      (required)
  startTime        datetime  (required)
  endTime          datetime  (required)
  reason           string

Example (POST):
POST /api/self-service/overtimes
{
  "employeeNumber": "EMP-0001",
  "startDate": "2026-09-10",
  "startTime": "2026-09-10T18:00:00",
  "endTime": "2026-09-10T21:00:00",
  "reason": "Month-end closing"
}

Example (POST) - overtime already approved in Zoho People (saved as
Approved):
{
  "employeeNumber": "EMP-0001",
  "startDate": "2026-09-10",
  "startTime": "2026-09-10T18:00:00",
  "endTime": "2026-09-10T21:00:00",
  "reason": "Month-end closing",
  "status": "Approved"
}

Example (PUT):
PUT /api/self-service/overtimes/456
{
  "employeeNumber": "EMP-0001",
  "startDate": "2026-09-10",
  "startTime": "2026-09-10T18:00:00",
  "endTime": "2026-09-10T22:00:00",
  "reason": "Month-end closing (extended)"
}

Example - Delete:
DELETE /api/self-service/overtimes/456

Response (POST/PUT/GET by id): OvertimeDto.

GET /api/self-service/overtimes (uses login)
  Lists the logged-in employee's overtimes. Query parameters: the
  paged parameters above, plus searchTerm, dateFrom, dateTo.
  Response: PaginatedList of OvertimeDto.

POST /api/self-service/overtimes/filings/{id}/send-approval-email
  Same behavior as the leave version: emails the employee's approvers
  an approve/reject link. Pending filings only. Response is 200 OK.

Notes:
- PUT/DELETE only work while the filing's Status is "Pending" and it
  has not been emailed for approval yet (HTTP 500 otherwise).
- PUT returns 404 if the id does not exist or the filing does not
  belong to the employee in employeeNumber. DELETE returns 404 if the
  id does not exist.
- With "status": "Approved", the overtime is saved as Approved. If the
  employee already has an Approved overtime on the same date with the
  same start and end time (to the minute), the request is rejected
  with HTTP 400, so re-sending the same approved overtime is not paid
  twice. A different time range on the same date is still accepted.
- An overtime (new or edited) is rejected with HTTP 400 while the
  employee has another Pending overtime filing on the same date.
- startTime and endTime cannot be equal (HTTP 400).

4. SHIFT
====================================================================
GET  /api/self-service/shifts          (list, uses login)
GET  /api/self-service/shifts/today    (today's shift, uses login)
POST /api/self-service/shifts          (create a schedule for a date range)
PUT  /api/self-service/shifts          (update the schedule for a date range)

POST creates one Shift row per calendar day from dateFrom to dateTo
(inclusive), all using the same start/end/break settings. Only the
time-of-day portion of startTime/endTime/breakStartTime is used; the
actual date comes from each day in the range.

PUT takes the same request body and sets the employee's schedule for
every day from dateFrom to dateTo: a day that already has a shift is
updated, and a day without one gets a new shift. There is no {id} in
the URL; the shifts are found by employeeNumber + date.

Request body (SelfServiceCreateShiftDto), for POST and PUT:
  employeeNumber      string    (required)
  dateFrom            date      (required)
  dateTo              date      (required, must not be before dateFrom)
  startTime           datetime  (required)
  endTime             datetime  (required)
  breakStartTime      datetime
  breakLength         decimal   (hours)
  isRestDay           bool
  requiresLunchInOut  bool

Example - POST:
POST /api/self-service/shifts
{
  "employeeNumber": "EMP-0001",
  "dateFrom": "2026-09-08",
  "dateTo": "2026-09-12",
  "startTime": "2026-09-08T08:00:00",
  "endTime": "2026-09-08T17:00:00",
  "breakStartTime": "2026-09-08T12:00:00",
  "breakLength": 1,
  "isRestDay": false,
  "requiresLunchInOut": true
}

Example - PUT (change Sep 10-11 to 10:00-19:00):
PUT /api/self-service/shifts
{
  "employeeNumber": "EMP-0001",
  "dateFrom": "2026-09-10",
  "dateTo": "2026-09-11",
  "startTime": "2026-09-10T10:00:00",
  "endTime": "2026-09-10T19:00:00",
  "breakStartTime": "2026-09-10T14:00:00",
  "breakLength": 1,
  "isRestDay": false,
  "requiresLunchInOut": true
}

Response (POST/PUT): list of EmployeeDutyScheduleDto, one per date in
the range (created by POST; created or updated by PUT).

GET /api/self-service/shifts (uses login)
  Lists the logged-in employee's shifts. Query parameters: the paged
  parameters above, plus dateFrom, dateTo, searchTerm, status.
  Response: PaginatedList of EmployeeShiftsDto.

GET /api/self-service/shifts/today (uses login)
  Response: EmployeeDutyScheduleDto for today's shift of the logged-in
  employee, or 404 if there is none.

5. TIMELOG - Check In / Lunch Out / Lunch In / Check Out
====================================================================
POST /api/self-service/timelogs                   (Check In)
PUT  /api/self-service/timelogs                   (Check Out)
PUT  /api/self-service/timelogs/lunch-out         (Lunch Out)
PUT  /api/self-service/timelogs/lunch-in          (Lunch In)

There is no {id} in the URL. Check Out/Lunch Out/Lunch In all locate
the existing TimeLog row via employeeNumber + date in the request body
(there is only ever one TimeLog row per employee per calendar day,
created by Check In). All four actions share the same request DTO
(SelfServiceCreateTimeLogDto); each action only reads the field(s)
relevant to it, but employeeNumber and date are always required by
model validation.

Request body (SelfServiceCreateTimeLogDto):
  employeeNumber   string    (required)
  date             date      (required)
  startTime        datetime  (used by Check In)
  endTime          datetime  (used by Check Out)
  lunchOut         datetime  (used by Lunch Out)
  lunchIn          datetime  (used by Lunch In)

Example - Check In:
POST /api/self-service/timelogs
{
  "employeeNumber": "EMP-0001",
  "date": "2026-09-04",
  "startTime": "2026-09-04T08:00:00"
}

Example - Lunch Out:
PUT /api/self-service/timelogs/lunch-out
{
  "employeeNumber": "EMP-0001",
  "date": "2026-09-04",
  "lunchOut": "2026-09-04T12:00:00"
}

Example - Lunch In:
PUT /api/self-service/timelogs/lunch-in
{
  "employeeNumber": "EMP-0001",
  "date": "2026-09-04",
  "lunchIn": "2026-09-04T13:00:00"
}

Example - Check Out:
PUT /api/self-service/timelogs
{
  "employeeNumber": "EMP-0001",
  "date": "2026-09-04",
  "endTime": "2026-09-04T17:00:00"
}

Response: TimeLogDto.

Note: Check In rejects a duplicate check-in for the same employee and
date (employee already has a TimeIn recorded for that date).

6. TIMELOG FILING
====================================================================
GET    /api/self-service/timelogs                   (list filings, uses login)
GET    /api/self-service/timelogs/{id}              (get one filing)
POST   /api/self-service/timelogs/filings           (create a filing)
PUT    /api/self-service/timelogs/filings           (edit a pending filing)
DELETE /api/self-service/timelogs/filings           (delete a pending filing)
POST   /api/self-service/timelogs/filings/approve   (approve a pending filing)
POST   /api/self-service/timelogs/filings/{id}/send-approval-email

Note: GET /api/self-service/timelogs and GET /timelogs/{id} return
timelog FILINGS, not time logs.

Used to file a manual correction/request (e.g. forgot to time in/out)
that requires approval, as opposed to a live Check In/Out. There is one
filing per employee per day, holding any of that day's four times:
check in, lunch out, lunch in and check out. Approving the filing
writes its times to the employee's time log for that day (the time log
is created if the employee has none for that date yet); times the
filing doesn't have are left as they are.

A correction that was already approved in Zoho People can be sent with
"status": "Approved" to update the time log right away, or created as
Pending and approved later with the approve call below.

There is no {id} in the URL for PUT/DELETE/approve. The filing is
looked up by employeeNumber + logDate (it must still be Status =
"Pending").

Request body for POST (CreateEmployeeTimelogFilingDto):
  employeeNumber   string    (required)
  logDate          date
  checkIn          datetime
  lunchOut         datetime
  lunchIn          datetime
  checkOut         datetime
  reason           string
  status           string    (optional) "Pending" (default) or
                             "Approved"
At least one of checkIn, lunchOut, lunchIn and checkOut is required
(HTTP 400 otherwise).

Example:
POST /api/self-service/timelogs/filings
{
  "employeeNumber": "EMP-0001",
  "logDate": "2026-09-04",
  "checkIn": "2026-09-04T08:00:00",
  "lunchOut": "2026-09-04T12:00:00",
  "lunchIn": "2026-09-04T13:00:00",
  "checkOut": "2026-09-04T17:00:00",
  "reason": "Forgot to time in due to system downtime"
}

Example - correction already approved in Zoho People (applied to the
time log right away):
{
  "employeeNumber": "EMP-0001",
  "logDate": "2026-09-04",
  "checkIn": "2026-09-04T08:00:00",
  "checkOut": "2026-09-04T17:00:00",
  "reason": "Regularization",
  "status": "Approved"
}

Response: { "id": <filingId>, "status": "Pending" | "Approved" }

Request body for PUT (UpdateEmployeeTimelogFilingDto) - employeeNumber
and logDate identify the filing to update. The four times, reason and
decidedBy replace the filing's current values, so send every time the
filing should have:
  employeeNumber   string    (required, identifies the filing)
  logDate          date      (identifies the filing; not changed)
  checkIn          datetime
  lunchOut         datetime
  lunchIn          datetime
  checkOut         datetime
  reason           string
  decidedBy        string
At least one of checkIn, lunchOut, lunchIn and checkOut is required.

Example:
PUT /api/self-service/timelogs/filings
{
  "employeeNumber": "EMP-0001",
  "logDate": "2026-09-04",
  "checkIn": "2026-09-04T08:00:00",
  "checkOut": "2026-09-04T17:30:00",
  "reason": "Corrected time"
}

Response: 200 OK (no body).

Example - Delete:
DELETE /api/self-service/timelogs/filings?employeeNumber=EMP-0001&date=2026-09-04

Response: 200 OK (no body).

Request body for approve (ApproveEmployeeTimelogFilingDto):
  employeeNumber   string    (required)
  logDate          date
  decidedBy        string    (optional, who approved it)

Example - Approve:
POST /api/self-service/timelogs/filings/approve
{
  "employeeNumber": "EMP-0001",
  "logDate": "2026-09-04",
  "decidedBy": "manager@example.com"
}

Response: { "id": <filingId>, "status": "Approved" }

GET /api/self-service/timelogs (uses login)
  Lists the logged-in employee's timelog filings from dateFrom to
  dateTo, ordered by logDate. Query parameters: dateFrom, dateTo,
  pageIndex, pageSize.
  Response: PaginatedList of EmployeeTimelogFilingDto:
    id, logDate, checkIn, lunchOut, lunchIn, checkOut,
    employeeID, employee { firstName, middleName, lastName },
    reason, status, decidedBy, isNotifyEmail, notifyEmailSentAt,
    created, lastUpd, createdBy, lastUpdBy

GET /api/self-service/timelogs/{id}
  Response: EmployeeTimelogFilingDto of that filing.

POST /api/self-service/timelogs/filings/{id}/send-approval-email
  Same behavior as the leave version: emails the employee's approvers
  an approve/reject link. Pending filings only. Response is 200 OK.

Notes:
- An employee can have only one filing per day. A new filing for a
  date that already has a Pending or Approved filing is rejected with
  HTTP 400 (edit the Pending one with PUT instead); a Rejected filing
  does not count. This also means re-sending the same filing does not
  record it twice.
- Only filings with Status = "Pending" that have not already been
  emailed for approval can be edited/deleted (HTTP 500 otherwise).
- If the employeeNumber is unknown or no pending filing is found for
  that employeeNumber + logDate, PUT/DELETE/approve return 404.
